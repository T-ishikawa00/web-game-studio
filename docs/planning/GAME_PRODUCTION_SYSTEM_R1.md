## A–Fの判断ゲート
| Phase | 作るもの | 確認 / 停止条件 |
|---|---|---|
| A テーマ/核 | 操作対象、目前の目標、失敗/再挑戦、見た目の変化、快感、短尺の見どころ、視聴後にも遊ぶ理由 | テーマはHumanが選択。全体のステージ設計を先にしない |
| B 導入試作 | コアの楽しさが伝わる小さな冒頭。目安数分、作品に応じる | Human試遊。退屈/混乱/弱い核なら改良か中止。面数追加でごまかさない |
| C 中後半試作 | ステージ型:ルールの組合せ。成長型:移動/行動が変わる進化 | Human試遊。「攻撃10→20」の数値成長だけでは能力変化の証明にならない |
| D 逆算 | 想定する最終体験→難易度曲線→導入順→必要な長さ | A–Cが納得できてから総量を決める。先に面数を固定して埋めない |
| E 制作 | 必要最小限のコンテンツ、日英、音/操作/保存/性能/権利情報 | 表面的なバリエーションで量を増やさない |
| F Human受入 | オーナーが実際にプレイし判断 | 技術QA合格と面白さの受入を別々に記録。Humanが受け入れるまでfinalと呼ばない |

## 選考観点
見ただけで伝わるルール、明確な障害と目的、試行錯誤、気持ちのいい成功/失敗/変化、短尺動画に残る瞬間、視聴後の自分で試す動機、即再挑戦、適切なモバイル操作、独自の表現、個人で保守可能な範囲。

数値スコアだけで採用しない。迷った箇所、リトライ理由、操作ミス、途中離脱、驚いた瞬間を試遊観察として記録し、事実と解釈を分ける。Human未試遊を「良好」「合格」と記録しない。

## 作品ごとの最小記録
`docs/games/<slug>/` をHuman選択後に作成する。theme、phase、build version、試遊日/条件、観察、Human判断、未解決点、権利記録、リリースノートを保存する。ユーザー情報を必要以上に収集しない。ゲームIDは安定、保存schemaは明示、破壊的変更には移行または同意付きresetを設計する。

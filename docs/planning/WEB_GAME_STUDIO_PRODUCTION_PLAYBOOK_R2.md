## 1. 事業戦略：本数ではなく、選ばれる作品とAudienceを増やす

### 1.1 ポジション
- 自作の、すぐ遊べるWebゲームが初期商品。日英を第一級として扱う。
- 見た目は作品ごとに個性を持てる。共通化するのは読みやすさ・操作・保存・配信・検証の作り方。
- 初期公開の目安は引き続き10本前後。ただし、1〜3本段階の外部試遊・作品単位の見せ方検証を待たせない。
- 10本は目安であり、弱い作品を埋めるノルマではない。公開本数の変更や段階公開の実行はHumanが判断する。
- 最初の宣伝は入口となる1〜2作品に集中。他作品は回遊先・次の入口候補として育てる。
- 自社Portalと外部配信の契約は別。外部Portalから自社へリンク誘導できることや、同時配信可能であることを前提にしない。

### 1.2 当面の優先順位
1. 現在3本の実機・初見理解を確かめ、Tiny Deliveryで音と反応の制作基準を作る。
2. 使える小さな品質基準を残し、現在3本の公開候補化と集客準備へ進む。
3. 次作は短い核と代表区間から。似た弱点を全編へ広げる前に修正する。
4. 外部反応がある作品の改善・追加コンテンツへ、新作と同等以上の投資候補を与える。

「大手並み」をファイル数・装飾量・テスト件数・制作費で測らない。同ジャンル／同規模の作品と、最初の操作、再挑戦、動き・音、最も密な盤面、動画の一場面を比べる。

### 1.3 キャパシティと支出
- 初期は**高密度の品質改善は1作品**を先行させる。他作品は独立した定型作業・回帰検証・集客素材準備を並行してよい。
- 「3本まとめて」は納品・管理の単位。毎回3本すべてを全面改修する意味ではない。
- 固定の開発/マーケ比率や絶対の制作日数は設けない。週次で、次の外部検証を止めている最重要ボトルネックへ配分する。
- 制作費はHuman時間、AI利用量（取得できた範囲）、追加ツール費、素材費、外注費を分ける。ChatGPT利用枠とAPI従量料金を混同しない。
- 企画時に試作の時間枠・追加現金支出上限を仮置きし、超過前に範囲縮小か追加投資を判断。早さのためにSecurity・保存・権利の品質基準を下げない。
- 今回の再開バッチでは追加契約・従量課金API・有料素材購入の権限は与えない。

## 2. 今後の新作制作：専門工程は持つが、Human確認を乱立しない

企画選択を除き、通常はHuman判断を以下の**3回**にまとめる。安全・契約・公開など不可逆な意思決定の確認は別。工程名を通過しただけでPASSを付けない。

| 工程 | Codex/Chatの作業 | Human判断 |
|---|---|---|
| 企画選択 | 1ページの企画カード。操作、目的、5秒で見せる核、視聴後に遊ぶ理由、近い3作品との差、最大のリスク、試作範囲 | どれを試すかをまとめて決める |
| A：核の試作 | 1〜3分の小さな実プレイ。少数の問題、即Undo/Retry。核を判断できる最低限の絵と反応。新規状態で触る | **H1：もう一度遊びたい核か**。継続／一点修正／保留 |
| B：代表区間の品質 | 冒頭1〜3面＋密な中後半代表1面。Art、直接操作、教え方、主要SFX、動き、成功失敗、日英、実機候補、9:16/16:9を一緒に作る。少人数初見テストをこの段階から手配 | **H2：この体験を全体へ展開する価値があるか**。品質見本を固定 |
| C：全体制作＋配布準備 | 終盤の到達体験から逆算し、必要な問題だけ作る。保存・解答再生・難易度・クロスデバイスQA。サムネ/短尺素材・権利・公開構成を並行準備 | **H3：試遊・配布先・実機・権利・運用を踏まえた公開判断** |
| D：公開後 | 流入→開始→進行→別作品→再訪を測り、一度に一つの仮説を改善。更新/拡張/新作/休止へ配分 | 毎週の経営判断に統合。細かな修正ごとの会議にしない |

H2前に、全18面・50面を量産しない。ただし既存のBatch 01をこの順へ戻して作り直さない。今回作るものは、将来用の工程と既存作品への必要差分。

### 2.1 H2の「品質見本」の定義
- 「どんなゲームか」「どこを触るか」「何が変わったか」が初動で伝わる。
- 最初の小さな成功と、中後半の深さの両方がある。
- 見た目だけでなく、操作の反応と音を含む代表区間が実装されている。
- 無音でも遊べる。縦動画でも意味が伝わる。実機確認ができなければ未確認を残す。
- 相性の悪いArtや音を、全編へ展開する前に発見できる。
- **Gold見本**は制作の基準という意味。外部未検証の作品をGold MasterやRelease Readyと呼ばない。

### 2.2 全体設計
問題数は必要な学習と深さから決める。「最短手数が少ない＝初心者にも易しい」と判断しない。導入は、操作を知る、短く成功する、同じルールを自力で使う、新しい条件を加える、の順。難問を序盤へ残す理由に保存互換性を使わず、安定ID/versionと移行で両立する。

## 3. 仕事の分担と、一括依頼の標準

### 3.1 分担
- Human：作品選択、面白さ・審美・聴感、公開、支出・契約、重大な方針変更。
- Chat：根拠付き企画、比較、仕様、Human感想の整理、次のバッチ化、取得できる実物のレビュー。
- Codexのprimary：現状確認、局所設計、実装、テスト、比較素材、統合責任。依頼を実行可能な内部作業へ分ける。
- 実プレイヤー：初見理解、再挑戦、継続、端末上の挙動の証拠。自動解答再生の代替ではなく別の検証。
- 専門家：特定の品質上限や契約リスクが明らかになったとき、時間・成果物を限定してレビュー。初期から全職種を固定費で雇わない。

### 3.2 モデルと委任
既存のTier policyを維持する。Astraは設計・品質判断・音と動きの統合・保存や共通Runtimeなど高リスク箇所、Sol相当は固まった仕様の通常実装、Luna相当は小さく可逆な定型作業。今回の主担当はHuman方針どおりAstra。

名称は設定や課金を自動変更しない。実際のmodel IDと使用可能な機能を確認し、未使用のモデルを使ったと報告しない。global設定変更・プラン変更は禁止。既存AGENTSの委任境界を保ち、書込み担当を無断で増やさない。primary以外の読み取りレビューと並列書込みは別の権限。

### 3.3 依頼を一回で完了させる形式
すべてのバッチを「目的／根拠／KEEP／変更範囲／品質条件／証拠／停止条件」で渡す。安全な可逆判断はCodexが選び、理由を記録して実装。ボタン一個、色一色、音一個ごとにHumanへ差し戻さない。

技術QA・コードレビュー・実ブラウザの視覚確認・試聴・Human受入は別欄にする。聴けない環境で波形や数値しか確認していない場合は、聴感PASSと書かない。

## 4. 品質を積み上げる標準

| 領域 | 毎作品に残す基準 | 毎作品で再発明しないもの |
|---|---|---|
| 遊び | 操作→結果→再挑戦と、固有の発見 | 演出で弱い核を隠さない |
| 見た目 | R5の読みやすさ、色＋形、少ない常設文 | 全ゲームを同じ配色・四角キャラに揃える義務ではない |
| 入力 | 直接操作、代替入力、誤操作抑制、Undo | スワイプ専用化、大きい操作パネルの復活 |
| Motion/VFX | 因果が読める、入力を遅らせない、キャンセル可能 | 演出都合の物理・tick・勝敗の変更 |
| 音 | 状態に対応する短い音、疲れないMix、無音でも成立 | 全アクションに大音量の音を付けること |
| Level | 正解手順の再生＋初見観察。密度/前提知識/分岐も評価 | 解けることを面白さと同一視しない |
| Delivery | 小さいbuild、復帰、保存、日英、実機、撮影 | 公開/外部配信の契約を一括で推定しない |

### 4.1 改善の停止基準
「もっとよくできそう」だけでは受入済み全体を開き直さない。次のどれかを変更理由にする：
- 実プレイで同じ理解障害・誤操作・離脱が繰り返される。
- 合意した品質見本や受入条件を満たさない。
- 追加投資を正当化する実測・明確な訴求仮説がある。
- Security、保存、権利、互換性の問題がある。

品質改善は、同じ場面のBefore/Afterで評価する。変化が聴き取れない／見分けられない装飾の追加を、作業量で正当化しない。小修正後に全件の撮り直しを繰り返さず、変更したビルドの影響範囲と証拠を一致させる。

### 4.2 変更の影響に応じたQA選択

再実行の根拠は **新しい変更・失敗・未解決リスク**。既存PASSを再利用するときは対象版・条件・依存先の不変を確認し、以前の実行と今回の実行を区別する。新しい差分を古いPASSで覆わない。対象QAが通った後の全問再生、大量画像・動画・長時間音源の再生成は標準にせず、必要になった理由がある場合だけ行う。既存テスト・hook・scanner設定や採用済みfrozen manifestを変更してPASSへ合わせない。

技術QA、AIの視覚確認/出力計測、Human聴感、実機環境、外部初見、全編ゲーム性、公開/法務/広告は別Gate。実機PASSは試験した条件のみ。NOT TESTED / PENDING / DEFERREDはそのまま残す。Humanの明示採用は当該対象だけを更新し、検証していないGateへ連鎖させない。

## 5. Audio/Motion方針

### 5.1 音源の選択
音の生成方法ではなく、必要な役割・品質・権利・費用で選ぶ。

| 方法 | 主な候補用途 | 留意点 |
|---|---|---|
| Codexによるローカル合成/編集 | 短いクリック、機械反応、抽象的な到着音、短いジングル | 生成AI音源APIとは別。ビープ音を置くだけで完成としない。音色・エンベロープ・繰り返しの聴感を確認 |
| 既存の権利確認済み素材 | 木・機械・環境など録音感が重要な音 | 加工、ゲーム内配信、動画使用、第三者配信、承継の条件を確認 |
| 外部生成サービス | 手元の方式で満たせないSFXやBGM候補 | アカウント、利用可能性、料金、生成時/ダウンロード時の条件、商用許諾を確認し、利用前にHuman承認 |
| 専門家への限定依頼 | 音色選別、Mix、Signature、最終耳のレビュー | 工数と納品物を限定。権利と制作記録を残す |

ElevenLabs等を契約しないと音が一切作れない設計にしない。反対に、無料の合成で質が足りないのに「上質」と自己評価して済ませない。不足を具体的に報告して次の判断材料にする。[S4][S5][S6]

### 5.2 順序
主要SFX → 動きとの同期 → 静けさと音量バランス → 必要ならBGM → 実機と聴感。

BGMは全作品への義務ではない。今回はまずSFXを評価できる状態を作る。BGM候補が必要なら、同じゲームでSFXのみ／BGM追加を比較する。SFX数や曲数は品質指標にしない。

### 5.3 Runtimeの最低条件
- 音を鳴らすのは受理されたゲームイベント。render、復元、resize、言語切替、テスト用snapshotだけで鳴らさない。
- 本物の入力に伴ってAudioContextを初期化/再開する。拒否・未対応でもゲームは続ける。過去の音を後からまとめて鳴らさない。[S4]
- muteと音量を簡単に変更可能にする。BGM/SFXは使う段階で分ける。大きな常設バーを復活させない。
- tab非表示、pause、モック広告、画面遷移、reset、Undo、捕捉モード切替で音とアニメーションの世代を管理。古い処理を取消す。
- 復帰時はユーザーのmute・ゲームの停止状態を尊重。iOS等では再度の入力によるresumeが必要になり得るため、実機検証を残す。[S7]
- 同時発音数、連打、優先順位、短いフェードを管理。全SFXを同じ最大peakへ正規化しない。短音単体とゲーム内の重なりを別に測る。
- 聞こえないと解けない問題にしない。無音・monoでもルールと状態を視覚で追える。
- 生素材/編集可能な原本は配布用とは分離。実配布は必要な素材だけ、相対パスで読む。全曲・全タイトルを先読みしない。

### 5.4 既存保存への具体的注意
GitHub版`src/prototypes/state.ts`のProgress.settingsは`reducedMotion`だけの厳密検証。そこへ音量を無造作に足すと、旧セーブ互換性を壊す恐れがある。

今回は音設定を小さな独立version付き設定へ分離する案を優先する。ローカル最新状態を確認し、必要な場合だけ移行方針を取る。無関係な設定や保存を全面再設計しない。storage拒否/破損時は安全な初期音量へ戻し、ゲーム進行を保つ。

### 5.5 来歴とクリエイター利用
asset ID、作成/取得方法、原本、加工履歴、発行元、作成/取得日、プラン/許諾、使用箇所、必要な表示を既存台帳へ記録する。値が秘密のAPIキーは記録しない。

音楽は特にゲーム内利用、実況・切り抜き、広告素材、外部Portal、事業承継の扱いを確認する。商用許諾と著作権保護の有無は別。既存曲・アーティストの再現や無権利のサンプルは使わない。[S5][S6]

自社側のContent ID登録で正当な実況者へ請求する運用は初期に採用しない。ただし第三者からの請求がゼロになる保証はしない。権利証跡、問い合わせ先、BGMを切れる設定を用意する。

## 6. プレイテスト・市場検証

### 6.1 テストを混ぜない
1. **技術テスト**：解答再生、決定性、入力、保存、ロード、実機。AIが正解を再生できても初見理解の証拠にはならない。
2. **初見テスト**：まず3〜5人程度を小さく目安にする。日英と実際の主要入力を意識し、事前説明なしで最初の操作と成功を見る。これは普遍的合格人数や統計的証明ではない。
3. **市場検証**：動画や作品カードから実際に来た人が開始・継続するか。無関係な大母集団の平均と比べない。

すでに制作した本人は初見テストの代わりにならない。過去に遊んだ人には別の観測目的を設定する。録画・個人情報は必要最小限、本人が理解して同意できる範囲。初期は成人の協力者から始める案を優先する。

端末借用・テスター手配・外部配信が未承認なら、それだけを未実施として残す。架空のテスター結果や「AIユーザー5人で初見PASS」は禁止。初見テスト手配を待つ間は、独立した配布準備・音や素材制作を進めてよい。[S1][S2][S3]

### 6.2 初期に追う指標
| 段階 | 最小の観測 | 判断例 |
|---|---|---|
| 露出→訪問 | 動画/投稿/作品名検索等の参照元別訪問 | 再生は多いが訪問がないなら、見せ場とリンク/作品名導線を見直す |
| 訪問→開始 | load success、意味あるfirst input。分母とtimeout定義を固定 | 起動や操作で詰まるなら集客を増やす前に修正 |
| 開始→進行 | 各面到達、retry、clear、離脱。見ているだけの時間と区別 | 同じ面で複数人が迷うなら教え方/難易度を検討 |
| 一作品→次作品 | related clickと実際の次ゲーム開始 | クリックだけを回遊成功にしない |
| 再訪・収益 | 適切な同意/識別がある場合のみ集計。承認後は実広告収益と費用 | 現金支出とHuman保守工数に対して追加投資を判断 |

撮影・自動QA・内部トラフィックは本番指標から除く。国・言語・端末・流入元・バージョンを必要な範囲で区別し、少ない件数の率だけで優劣を断言しない。

### 6.3 マーケティングの制作物
各作品に「実プレイからの5〜10秒の核」「9:16の短尺」「16:9の説明・実況用素材」「サムネ候補」「日英一文説明」を作る。尺は用途に応じて調整し、数のために動画を量産しない。

プレイヤーの困りごと→一手/調整→気持ちよい結果が見えるようにする。実際に遊べない機能や演出を広告用にだけ作らない。投稿・連絡・広告費・外部Portal申請は別承認。入口ゲームはTiny Deliveryを先行候補とし、実測で見直す。

公開直前はprototype/internal/designが通常配布へ混入しないことを確認。noindexはアクセス制御ではない。購入/契約/公開/外部連絡の承認は少数の一括判断にまとめるが省略しない。

## 8. 記録と工程自体の改善

### 8.1 常用文書は増やしすぎない
- 本書：運用方針と制作フロー。
- 現在地の短い記録：commit/未commit、受入済み、実施中、次バッチ、未承認の外部操作。
- 各作品の企画/仕様と既存の権利・素材台帳。
- 各バッチのReview：要点、代表画像/短い動画、QA、Human判断、制約。

既存R1〜R5を保存し、`AGENTS.md`には最新リンクと安全・受入境界だけを短く反映する。旧`GAME_PRODUCTION_SYSTEM_R1.md`には後継と過去時点である旨を明記し、古い「未着手」を現状へ誤適用させない。全文を複数箇所へコピペして二重管理しない。

### 8.2 証拠は必要なものを残す
今回のGitHub checkpointには、Human報告で980件中870件のQA証跡がある。今は整理を新しい大仕事にせず、そのまま保全。

今後は代表画面、再現に必要な実行条件、結果サマリー、入力列・seed・対象commitを優先。反復実行の全スクリーンショット/キャッシュは既存方針に従いローカルの無視領域へ置く。役立つ証拠は落とさないが、ファイル数を成果にしない。過去コミットの大掃除・履歴書換えは別承認。

### 8.3 作品ごとの振返りは短く
各作品の受入/外部試遊後に、(1)再利用する改善、(2)次作でやめる作業、(3)まだ仮説の点、を最大3点程度へまとめる。

一作品の好みを全作品に強制しない。複数作品で再現したものを共通Runtime/制作レシピへ昇格する。プロセスを改善しても、受入済み作品を全件遡及改修する義務にはしない。

# 9. 次にCodexが実行する一括バッチ
## Production System R2 Adoption + Tiny Delivery Craft Pilot 01

### 9.1 目的と停止点
本書を現行運用へ反映し、Tiny Deliveryの操作・結果を伝える音と動きを実装し、無音と比較できるレビューを作る。**計画だけで止まらずローカル実装・QA・試聴素材まで行い、Humanの耳と手による判断を1回だけ残す。**

これは公開品質の最終保証ではなく、今後に再利用するAudio/Motionの最初の品質見本。

### 9.2 開始時の確認と保全
- CWDを厳密に確認。既存dirty/untracked成果を異常扱いしてclean/resetしない。
- HEAD/upstream/worktree、最新ローカルの57問・導入改善を確認。Chatのremote SHAは過去の基準点であってcheckout指示ではない。
- 旧成果はRepo内の無視領域で保全。空白パスの問題の再発防止を確認し、shell文字列連結でパスを壊さない。
- `AGENTS.md`、`START_HERE`、`SECURITY.md`、R5受入、最新導入改善レポート、現在の音/アニメーション/保存を読む。Windowsローカルの最新状態を正本に差分作業する。
- 新しい共有ゲームエンジンや大きな管理システムは作らない。既存のprimary責任・委任境界を維持する。

### 9.3 文書整理を先に短く済ませる
本書を`docs/planning/WEB_GAME_STUDIO_PRODUCTION_PLAYBOOK_R2.md`へ保存。AGENTS/既存制作R1/現状メモへ、最新方針への短いリンクと更新点だけを反映する。

局所導入修正へのHuman発言は正確な範囲で記録する。全編・初見・実機・音・公開を受入済みにしない。まず文書の完全性を追って何日も使わず、次項の実装へ進む。

### 9.4 今回の実装対象
**Tiny Deliveryのみ**を新しいAudio/Motionの適用先にする。Lightwork/Two Waysは新しい音や装飾を追加せず、共有変更の回帰確認だけ行う。

対象シーンは、実在する既存問題から導入一つ・交差/待機の中盤一つ・密な終盤一つを選ぶ。新しい問題を作らない。実装自体は同じイベントを使うTinyの全18問で成立させ、代表区間を比較素材にする。

### 9.5 音の設計案
音の性格：**小さな玩具の機械。短い、乾いた、控えめ、成功だけ少し明るい。**

必要なイベントは概ね8〜12種以下から始める。音が不要なら無音も設計結果として認める。

| イベント | 意図 | 注意 |
|---|---|---|
| 矢印の変更 | 小さな機械クリック | 連打しても刺さらない。変更が受理された時だけ |
| 待機設定の変更 | 矢印とは違う小さなtick | 開くだけ/値が変わらない操作で重複させない |
| Undo/調整へ戻る | 戻ったと分かる静かな反応 | 衝突音や成功音を再生し直さない |
| 出発 | 短い起動音 | 起動音のためにシミュレーションを遅らせない |
| 停止/再開 | 必要ならごく短い反応 | 無音で明確なら不要。再開で過去の起動音を重ねない |
| 到着 | 荷物が収まる短い音 | 各到着一回。renderごとに繰り返さない |
| 衝突 | 控えめなbonk | 罰のような爆音・長い不快音にしない |
| 問題クリア | 短い達成音 | 到着音との重複音量を整理する |
| 全編クリア | 短い独自のSignature候補 | 長く引き止めず、音なしでも結果が分かる |

常時モーター音、全tickのクリック、長い残響、全操作の派手な音は初期に入れない。

代表3音程度は2〜3候補を作って比較し、同じゲーム内で選別する。すべての音を数十候補ずつ生成するバッチにしない。

### 9.6 制作方法と音素材
初期は承認済みローカルツールと、由来の明確な自作合成/編集で候補を作る。生成AIサービスへプロンプトを送ること、APIキーを探して使用すること、無料/有料クレジットを消費することを今回の権限に含めない。

必要なら、発音のエンベロープ・複数音色の重なり・フィルタ・短いフェード等を使うが、単純なbeepが並ぶだけなら不足と判断する。既存の音があれば由来を確認して再利用する。

希望する質感が手元では出せない場合、対象音、目的、外部方式候補、利用条件、必要費用をまとめて報告する。勝手な契約はせず、他の許可範囲の実装・比較資料は完了させる。

今回はBGM生成・契約を必須にしない。比較用にBGMを使う場合も、既存かつ権利確認済み素材に限定し、BGMなしでも品質を判断できるようにする。

### 9.7 動きの変更範囲
- 矢印変更、出発、移動/曲がり、停止、到着、衝突、クリアのうち、因果や触感に意味がある箇所だけ調整する。
- 小さい圧縮・反発・短いハイライトなどを使ってよいが、採用済みのR5形状・配色・画面配置を再デザインしない。
- 判定の座標・tick数・待機・衝突・勝敗は不変。アニメーションのために答えが変わってはいけない。
- 入力結果はすぐ反映。装飾の再生完了を次入力の不要なロックにしない。
- pause/Undo/restart/layout change/page hideで古い演出と音を取消せる。
- reduced-motionでは必要な情報を残して動きを弱める。演出がないと位置が分からない設計にしない。

### 9.8 小さいAudio Runtime
既存実装を調べてから必要な薄い層を追加する。event ID/variant、gain、mute、音源の寿命、発音上限、失敗時の無音fallbackを持つ程度。今回使わない複雑なMixer/楽曲生成画面は作らない。

設定画面の「音声なし」は、実際の状態に合う短い音設定へ置換する。初回の音は本物のゲーム操作で初期化/再開し、既存muteを尊重する。ゲームを始めるための余計な全画面メニューを増やさない。初期音量は控えめな仮値から、実際の試聴で選ぶ。

第5節のブラウザ・保存・Security・音の来歴要件を適用する。

### 9.9 同条件の比較
内部Reviewに以下を用意する。
- A：今までの無音・既存Motion。
- B：改良Motion・無音。
- C：B＋新しいSFX。

同じ問題、入力順、速度、表示サイズを使う。比較のためにゲーム状態を共有して壊さない。Aは安全に保全した元版の録画でもよく、本番用に旧新2エンジンを残さない。B/C切替は開発比較用。公開UIへ実験スイッチを増やさない。

Humanは「音がある方が大きく感じる」だけでなく、操作理解、達成感、繰り返しの疲れを比較する。

### 9.10 QAとレビュー
必須：
- 最新ローカルの全57問の解答/ルール・入力・保存回帰。影響箇所を中心に既存スイートを再利用する。
- 音の多重発火、連打、音源欠落、mute保持、storage失敗、tab hide/復帰、モック広告pause、Undo、同じゲーム再読込、表示切替。
- 無音/音あり/reduced-motionでゲーム結果が一致。
- 日英・通常/9:16/16:9、Portalと旧fixture、prototype/Design build隔離。
- 同時発音時のclip、不要な音の残留、追加byte数・リクエスト数、CPU負荷の変化を可能な範囲で測る。実測できない値は捏造しない。
- 実機なしはNOT TESTED。波形/ピーク測定だけなら聴感確認済みとは書かない。
- Secret ScanとDiff。既知1候補の根拠・限定承認は維持、新規候補は別停止。

一つのReview Packに、同条件A/B/C、試遊URL、代表SFX試聴、導入/中盤/終盤の短い操作映像、音来歴とQA要点、残課題を集約する。全画面の何百枚ものスクショを新たにcommit候補へ増やす必要はない。

録音経路で実際に音が取れていない動画を「Audio確認済み」としない。ブラウザ録画が無音なら、波形ファイルの試聴や実ゲームURLも添え、同期の聴感確認はHumanに残す。編集で後付けした音をランタイム同期の証拠と偽らない。

初見試遊・物理スマホの短い確認手順、ゲーム内実プレイを使う日英の動画Hook各2案も同じReviewへ添える。録画送信や外部募集は実行しない。

### 9.11 権限・停止
許可：このRepo内のローカル文書・実装・自作音候補・編集・既存環境でのQA。必要な制作資料を読むこと。

禁止：stage、commit、push、checkout/resetによる成果破棄、履歴書換え、remote変更、deploy、Domain購入、広告/本番Analytics、契約、外部API/音源生成の新規利用、実ユーザーへの勝手な連絡、他Repoやglobal設定の変更。

最新のdirty成果を保全し、想定外の第三者差分があれば破棄せず分離。範囲外出力や新規Secret、未承認費用、権利不明素材、ルール変更が必要ならその部分で停止し、独立して安全な作業は進める。

最後は**「Craft Pilot実装・技術QA済み、音と反応のHuman受入待ち」**で停止する。受入後に、既存の導入改善とこのpilotを識別可能なcommit単位でまとめて保存する提案をする。実際のcommit/pushは次の明示承認まで行わない。自社公開や外部配信の許可に拡大しない。

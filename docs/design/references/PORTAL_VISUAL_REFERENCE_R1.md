## 6. 今回まとめて実装する画面と操作

### 6.1 Home / ゲーム一覧

- 採用画像の明るい棚を、実際のHTML/CSS/コンポーネントで構築。
- 10件の内部デザインデータで密度を確認。2件・0件でも誇張なしに成立させる。
- カードは画像、常時読める作品名、短い行動説明、必要ならタグ1〜2個。時間・架空評価なし。
- 全体を一つの主リンクにする場合、Playアイコンは同じリンク内の視覚表現とし、buttonや別aを入れ子にしない。
- 実際の公開作品の主カードは同じ言語のPlayへ直結する。詳細ページは任意の入口として残す。
- 検索は作品名・短い説明・タグ・日英の名前を使う軽いカタログ内処理。通信・課金検索・AI検索を追加しない。
- 分類と検索は組み合わせて動作し、件数・選択状態・0件・解除を明確にする。
- 推薦は`運営のおすすめ / Studio picks`など、編集順であることを表す。個人最適化や実人気を装わない。
- 新作表示/新しい順は実際の公開日に基づく。日付がなければ隠す。fixtureの試験値は実公開記録へ流用しない。
- HeaderのNewとchipのNew等、同じ動作の重複は最小化する。Aboutは小さな補助リンクまたはfooterへ。
- 棚で使った検索/分類/並びを、戻ったときに軽い方法で維持。storage不可なら通常の一覧へ安全に戻れる。
- 戻りURLを外部へ無検証で転送する仕組みにしない。タブ、新規ウィンドウ、通常のリンク動作を壊さない。

### 6.2 ゲーム詳細 / プレイ画面

- 詳細ページにも同じ色・文字・カード規則を適用。直接訪問時にPlayがすぐ分かる。
- プレイでは巨大Heroを使わず、小さなロゴ/戻る/作品名を中心にしてゲーム領域を優先する。
- 横/縦の縦横比を尊重。画面回転で保存を勝手に初期化しない。Fullscreenや音量は本当に機能する場合だけ表示。
- 読込中、失敗、再試行、保存拒否、破損/未知版、リセット確認、モック広告の停止/復帰を維持する。
- 読込率が分からないときに架空の%を表示しない。ロード不能時に無限スピナーで終えない。
- 既存DOM IDに依存するスクリプトを確認し、UI差替えでイベント・dialog・復帰を壊さない。
- QAパネルは内部用として保持。一般ユーザー想定の周辺UIと分け、検証能力を削らない。
- 関連作品は最大3〜4件程度。自分自身、未公開、重複を除く。該当作品がなければ出さない。
- 広告は既存mock/disabledのみ。巨大な広告予定地や、本番広告のコードは入れない。

### 6.3 Mobile / 日本語・英語

- Desktop Homeの画像を縮めるのではなく、共通の見た目を小さい画面へ組み替える。
- ロゴ・言語切替・検索は必要なら2段。Heroはさらに圧縮し、挿絵は文字や作品画像に重ならないようにする。
- フィルタは少数の短いラベルで折り返す。画面全体の横スクロールを発生させない。
- タイトルと一言はタップ前に見える。文字拡大・長い英語・日本語の改行を確認する。
- 明示された`/ja/`、`/en/`を尊重し、場所・推測言語で勝手に転送しない。
- 言語切替は同じ作品・同じ種類の画面へ。保存キーは言語別にしない。
- 翻訳は画像から機械的に拾わず、対象ゲームの意味に合う実テキストを管理する。
- Keyboard focus、dialogの閉じる/復帰、iframeからの離脱を確認。Hoverのみの情報、強制的な大きい動きは避ける。
- Desktopの方向採用を、Mobile/Playの最終Human承認として扱わない。実装後に同じ確認セットで提示する。

### 6.4 その他の画面

About、Privacy、Terms、Contact、404、0件、画像失敗、JSなし等の外観を統一する。法務文章の内容をVisual作業のついでに確定・拡大せず、草案・未承認の状態を維持する。実際の問い合わせ先がなければ捏造しない。

## 7. 仮Artworkと内部プレビュー：見た目を妥協せず、公開作品も偽装しない

ここは重要。実ゲームが0件であることを理由に、採用画像とかけ離れた無地の箱だけを出して完了しない。一方、仮の10作品を実際にリリースしたように見せない。

### データ・ルート

- **共通のHome/Card/Play周辺コンポーネント**に、実registryまたはデザイン専用データを渡す。見本だけ綺麗で本体UIが別物になる作り方を避ける。
- デザインデータは実`games`/`themes`と分離する。`released`へ変えて架空作品を増やさない。
- 見本はローカル専用の明示モード/ルートにし、画面上に「Design preview — 仮の作品を使った見本」と分かる控えめな表示を付ける。
- 仮カードのクリック先は「画面見本／ゲーム未制作」と明記した内部のPlay周辺見本。ゲームが動いているふりをしない。
- `connection-lab`は保存・モック広告等を検証する本物の内部fixtureとして別導線で維持する。
- 追加するデザイン専用ルート・データ・Artworkは、通常buildで配布物へ混入させず、明示的なpreview buildでだけ利用する。クエリ、localStorage、CSS非表示だけに分離を任せない。
- 軽いbuild設定とasset配置で分離し、新たなCMSや権限システムを作らない。dev/previewの実URLと使うmodeを記録する。
- 既存の通常R1ビルドはそれ自体が内部ローカル用である。本作業でデザインデータを除外しても、本番公開の全審査が済んだとはしない。

### 画像・素材

- まず添付画像を実際に開いて確認する。読めない場合は、想像で代替せずその点だけをHumanへ確認する。
- 原画像を`docs/design/references/`等のRepo内へ原本保存し、本書との対応を残す。原名でもよく、コピー名はCodexが整える。
- **Webページ全体を1枚画像として貼り、透明リンクを重ねて完成扱いすることは禁止。** タイトル、説明、ボタン、検索、フィルタは実装する。
- スピードのため、添付した自社Concept画像からArtwork部分・装飾部分だけを切り出し、内部見本で暫定利用してよい。文字、タグ、ボタン、カード外枠ごと切り出さない。伸ばしすぎたボケや不自然な境界は確認する。
- この切り出しは第三者サービスのスクリーンショット転載ではなく、添付Concept画像に限る。Poki/Steam/Nintendoの画像は自社素材へ転用しない。
- 外観を新しくし直すための別案生成、無許可の有料生成、素材購入、ツール契約は行わない。良質な素材が必要で手持ちでは満たせない場合は、勝手に粗い代用品で合格にせず、必要な差分を報告する。
- 出所・加工（元ファイル、切出し範囲、暫定利用、差替え要否）を既存Asset台帳へ短く追記する。巨大な別の管理システムは不要。
- 画像内の`Clockwork Repair Workshop`等は仮名・仮画であり、別repoの`からくり修理工房`の正式画像ではない。画像中の説明の取り違えを実ゲーム仕様へ持ち込まない。
- 実ゲームの公開時は、そのゲームの内容に合う権利確認済みの画像へ交換する。マスコット・ロゴ・AI生成物の法的確認を本画像の採用だけで完了扱いしない。

### 素材が混在した状態のQA

10枚のうち一部を、内部用のピクセル表現・抽象図形・機械的な図案へ切り替えたストレス確認を用意する。配置と情報規則が保たれるかを確認するためで、採用Concept Aの可愛い基準画像を全面置換する指示ではない。正規QAへ戻す操作も明確にする。

| 起動URL | 実プロセス/モード/ポートを確認。4321/4322を混同せず、クリックして使えるURLを報告 |
| 探索 | 検索、フィルタ、併用、解除、0件、日英の名前、戻るを実操作で確認 |
| カタログ | デザイン10件/2件/0件、混在Artworkを確認。実公開ゲーム0件という記録は維持 |
| Play | 内部fixtureの起動、読込失敗・復帰、保存・reload・言語跨ぎ、破損/拒否/未知版、reset確認 |
| モック広告 | pause/resume、skip/未表示/失敗、報酬一回性、ゲーム移動後の間隔、フォーカス復帰 |
| 日英 | Home/一覧/詳細/Play/補助画面。長い作品名や日本語改行。英語でだけ情報が欠落しない |
| 画面幅 | 320/390/768/1024/1440px、参照比較用1672×941を目安に確認。代表画面で200%拡大。横溢れ・重なりなし |
| 入力 | Mouse/Keyboard/Pointer。Tab・Enter・Escape・dialog・iframeを確認。エミュレーションとスマホ実機を区別 |

| ネットワーク/軽さ | 無許可の外部ゲーム/広告/解析/フォント通信なし。Homeが全ゲームを取得しない。画像寸法/適切なサイズと遅延読込を確認 |
| Visual | ブラウザの実装画像とConcept画像を並べて自己レビュー。違いを説明し、合意外の劣化はHumanに出す前に修正 |

### Visual自己レビューの重点

1. 白系の明るさ、可愛い挿絵、Artworkの楽しさ、ライムの操作表現が残ったか。
2. Hero縮小後も雰囲気が残り、ゲームが主役になっているか。
3. カードが画像＋タイトル＋一言として読めるか。タグばかり増えていないか。
4. 画像の代わりに空箱、A/B/C、長文カードを並べていないか。
5. 画像生成物の偽機能・未測定時間・仮作品を、実データに見せていないか。
6. Mobileが単なるPCの縮小ではなく、同じ世界観で自然に操作できるか。
7. 生成画像の不揃いや誤字をそのまま実装していないか。

軽い差異や実装上必要な調整は短く記録して進める。延々とピクセルの一致だけを追わない。一方、背景・Artwork・カード構造等の大きな違いを「雰囲気再現」で済ませない。

## 10. Humanへ返すもの

一つの完了報告にまとめる。ファイル移動や複数の設定をHumanへ押し戻さない。

1. **実際に開けるローカルURL**：日英Home（デザイン見本）、Play周辺見本、内部接続テスト。通常データ/見本データの区別を添える。
2. **実装から撮った画像**：Desktop Home EN（参照比較）、JA Home、Mobile Home、Desktop/Mobile Play。生成画像を実装証拠として再掲しない。
3. **KEEP/CHANGEの結果**：採用画像から残したもの、5点の修正、追加差異と理由。
4. **QA表**：PASS/FAIL/NOT TESTED、実行コマンド、対象幅、実機かエミュレーションか。
5. **Repo状態**：branch、基準HEAD、変更一覧、worktree。commit/push/deploy/外部有料操作はいずれも0。
6. **残項目**：公開素材、正式名、公開規約、広告、実ゲーム制作など、今回の範囲外だけを整理。

Humanへ求める確認はまとめて三つ程度にする：
- PCのHomeが採用画像の良さを保っているか。
- スマホでも選びやすく、Play周辺の見た目が同じ方向でよいか。
- ブラウザで触って気になる点は何か。

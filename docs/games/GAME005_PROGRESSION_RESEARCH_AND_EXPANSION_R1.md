## 1. 推奨と今回の判断範囲

推奨は **A「住み継ぐ島 — 地区の用途を選び、元の集落とつなぐ」**。同じ島への愛着を積み上げながら、地区ごとに「何を先に整えるか」「どこを暮らしの場所として残すか」を変える。新資源や住民の世話を増やす前に、**投資で島の使い方・人の動線・眺めが変わること**を継続動機にする。

直ちに10時間分を量産しない。まずMVPの橋完成後に続く **「橋の向こうを、暮らしの入り江にする」5〜10分の設計Slice**で、次の発展を見たい気持ちが生まれるかを確認する。10時間は累積プレイの設計仮説であり、提供済みコンテンツ量・継続率・必達時間ではない。

## 3. 調査方法と要点

[10作品の一次情報・プレイヤー評価・出典台帳](GAME005_PROGRESSION_RESEARCH_R1_SOURCES.md)を併読。必須6作品と、独自選定4作品を比較した。選定は人気順ではなく、経営負荷／景観／局面変化／放置という異なる構造を調べるため。

- **FACT**：開発元・公式販売ページが説明する仕様。マーケティング文言を実測の面白さとしない。
- **PLAYER REPORT**：本文を確認した個人の体験。版・機種・嗜好の偏りがあり、市場全体の評価ではない。
- **OBSERVED**：今回の競合の実操作検証は0。公開ページの読取とローカルsource・凍結照合のみ。
- **HYPOTHESIS**：以下のGame005への設計推論と数値予算。**UNKNOWN**：実プレイで未検証の結果。

| 調査論点 | 読み取れたこととGame005の判断 |
|---|---|

## 5. 推奨Aの30分 / 2h / 10h

## 6. Expansion Slice設計 — 橋の向こうの入り江

**設計のみ、所要5〜10分は検証目標。現在遊べるのはAccepted MVPで、このSliceの試遊URL・動画・実測は存在しない。**

### 最小追加と因果

| 項目 | Sliceの具体仕様案 |
|---|---|
| 開始 | 原MVPの橋完成後、3人・2資源・原施設をそのまま引き継ぐ候補。既存対岸の土地を利用 |
| 新しい発展段階 | 「通れる対岸」から「人が使う入り江」へ。地区の状態が通行可能→整備中→暮らしが見えるに変化 |
| 新しい判断 | ①人が集まる広場と、人が島を巡る回遊路、どちらに先に投資するか。②広場を海際／木陰の2地点から選び、回遊路をどちら側へ接続するか。もう一方の発展は永久ロックしない |
| 新しい景観 | 小道・護岸の足場→縁台・植栽・灯りのまとまり。完成後、余剰の住民だけが広場で休む。新しい作業が来れば自動復帰。経済処理を休憩で遅らせない |
| 新しい機能 | 建物単体から「接続された空間」へ。広場だけなら短い往復と休憩、回遊路だけなら既存の橋→海辺→木陰→橋を巡る散歩、両方なら途中で広場に立ち寄る。住民の余剰時間だけ使い、仕事は自動で優先 |
| 景観と機能の関係 | 広場の位置によって回遊路の接続部分が自動で変わり、縁台・木立・通行のまとまりができる。個別の道マスを敷く操作は不要。資金・生産倍率は発生しない |
| 最小追加量 | 資源+0、住民+0、島+0、交易変更+0、独立生産chain+0。公共空間1、回遊路1、地区接続工事1。追加概念は「空間がつながると利用のされ方が変わる」1つ |
| 目標 | 「橋の向こうを、暮らしの入り江に」。3状態条件＝接続完了＋広場完成＋回遊路完成。実際に散歩を観察する回数や時間を達成条件にしない |
| 終端 | 両方の発展が残り、最初の村と入り江が1画面で見える。次の高台の用途を1つ予告して終える。続きの架空のボタン・購入・実広告は出さない |

「広場先行／回遊路先行」は経済最適化の問題ではなく、島に最初にどんな生活を生むかという選択。広場先行では立ち寄り・滞在、回遊路先行では島を渡って巡る動きが先に見える。どちらにも架空の効率bonusを付けない。**場所と動きの変化だけで意味のある判断と感じるかはUNKNOWN**。好みの違いにすぎず次の発展を考えられないなら、この設計の核心は未成立として戻す。

### 初期バランス案と5〜10分の進行表

数値は紙上の開始案。原MVPのBALANCEは変更しない。候補開始時の残資源は実際のMVP完了値を継承し、足りない分だけ自動採集・既存明示出荷で賄う。テスト専用開始fixtureは保存と分離し、通常プレイ実測として扱わない。

**時間整合の注意**：上記工事は移動を除けば合計72 worker-secondsで、2人稼働なら36秒程度。既存採集・出荷速度から考えて、熟練最短経路は5分未満になり得る。5〜10分は配置比較・初見理解・観察を含む想定であり、待機による保証ではない。通常等速プレイで計測し、短すぎても追加納品やタイマーを機械的に足さない。意味ある変化が少なければ、Sliceを短いまま評価するか次の1判断を設計し直す。

仕事のない住民だけが新しい空間を利用する。新たな工事・採集・出荷が発生したら、経路上の安全な接続点で自動復帰する。散歩のために仕事を遅らせる場合は、実作業員の長い遊歩をやめて拠点近くの短い所作へ縮小する。住民を強制idleにして見せ場を作らない。既存採集目標に達した状態と、資源不足で全員仕事中の状態を分けて検証する。

### UI・Craftを守る具体条件

- Gold Galleryで新しい候補を最大3枚だけ追加表示。新しい全画面管理panel・常駐quest一覧・住民一覧を作らない。現在選択中の費用と結果が短く分かること。
- 日英の仮copy：`入り江を整える / Shape the cove`、`木陰の広場 / Shaded commons`、`入り江の回遊路 / Cove walk`。島に長文を重ねない。
- 工事中の骨組・運搬・完成の変化は原MVPの表現密度を基準にする。色替えだけの完成状態、最初から完成モデルの出現だけで済ませない。
- 海際配置は水辺の縁台、木陰配置は木立を囲む空間。経済効果は同じ。広場と元の母屋が両方読めるカメラ、360/390pxでの島の占有範囲を比較する。
- アイドル時の休憩は自動演出で、住民の世話や来客数を新しい資源にしない。工事中の回遊でcritical pathが変わらないようにする。

## 7. 保存・Web・offlineの判断

本工程では保存code・key・schemaを変更しない。将来Sliceは独立candidateにし、MVP専用key `tinlumo:game005:island:live-ui:r3-2` を書き換えない。候補は別version付きnamespaceを使う設計。MVPの続きは、Humanの明示的な「この島を拡張候補へコピー」操作で検証済みversion2を読み取り、候補versionへ変換して別保存する。旧データはそのまま保持し、破損・保存失敗・競合なら開始成功を表示しない。今回はコピーも実行しない。

| 観点 | 推奨仕様・検証対象 |
|---|---|
| 途中保存 | 原MVPの保存契約を引き継ぐ。工事・出荷確保・支払済み判定・選択・設定を復元。移行を成功と扱う前に読戻し検証 |
| 10hへの保存対策 | 再訪価値を失わないため、Full前にlocal export/importの必要性を判断。生の状態を外部へ送信しない。Cloud Save/accountは追加しない |
| 破損・quota・拒否・2tab | 元データ保全、正直な一時保存表示、revision競合で片方の書込みを止める。自動resetなし |
| リソース予算 | 最大6人・5地区を暫定上限。アクティブsimulationは1島だけ。全NPCに複雑なneeds計算を持たせない。地区解放で素材を段階loadする可否は将来計測 |
| 前景自動作業 | 採集・運搬・建設を自動化し、プレイヤーは投資と配置へ集中 |
| 背景・終了中 | Sliceでは進行停止。hidden / page lifecycleで保存し、復帰時の巨大dt精算なし。次の計画を短く復元表示 |
| offline精算の長所 | 短い再訪でも完成や蓄積を受け取れる。長い進行待ちを短縮できる可能性 |
| offline精算の短所 | 成長場面を見逃す、戻る義務、時計変更・二重精算、経済膨張、保存契約とQAの増加。新資源より大きい設計変更になり得る |
| 将来検討するなら | Humanが開始した工事1件だけの有限精算を別比較。無限収益・日次bonus・通知を前提にしない。Sliceに混ぜない |

ブラウザは背景のタイマーや描画を抑制し得るため、常時稼働を前提にしない。[MDN Page Visibility](https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API) ローカル保存の永続性も保証できず、WebKitにはbest-effort保存のeviction方針がある。[WebKit Storage Policy](https://webkit.org/blog/14403/updates-to-storage-policy/) PWA・Service Worker・App Store化をここから自動追加しない。

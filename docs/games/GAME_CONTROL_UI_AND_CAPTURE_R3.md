# Part I — 3作品共通の操作UIデザイン原則 R1

## 1. 到達点

> **盤面を邪魔せず、押すべき操作がすぐ分かり、押した感触と結果に納得できる、小さく精密なゲーム用操作UI。**

「かっこいい」を、黒背景、ネオン、ガラス、金属の過剰装飾とは解釈しない。現在の庭・絵本・玩具のArtに合う、形の精度、読みやすさ、機能の整理、短い反応を作る。

### KEEP / CHANGE / AVOID
| KEEP | CHANGE | AVOID |
|---|---|---|
| 盤面Art、キャラクター、ルール、問題、現在の世界観 | 盤面下に散らばる長文ボタンを、まとまった操作エリアへ | 色だけ替えた既成Webフォーム風UI |
| Portal本体とprototype分離 | 有効/無効/進行中/成功の違い | 全ボタンを濃色にして主従を消す |
| Undo/保存/再開の意味 | UI文言を短く、意味を保って統一 | 読めない薄文字、Hover前提、アイコンだけで意味を察させる |
| 既存の図解/チュートリアルの内容 | ガイド・補助操作の位置と出し方 | 濃い外枠や影を何重にも足す、全画面の作り直し |

## 2. 優先順位は「重要度＋今の状態」で決める

Primaryを常時置くために、存在しない「開始」や押せない「次へ」を大きく表示しない。

- **盤面操作が主役の作品:** ひかりは鏡、ふたりは方向入力が実際の主操作。解答中はUtilityだけでもよい。
- **進行状態のある作品:** 配送は、その時点の「出発 / 一時停止 / 再開 / 調整する」が主操作。
- **成功後:** 次の面へ進める状態になって初めて「次へ」をPrimaryにする。
- 常設の「遊び方 / ヒント / 設定」は補助。盤面から離れず短い操作で開ける位置に置く。

### 操作エリアの構成
1. 盤面と視覚的に結びついた、浅い一つの操作バーを基本とする。幅は盤面か有効操作領域に合わせ、ページ全幅の大きなカードにしない。
2. Undo/RestartはUtility group。実行/進行操作はAction group。弱い区切りと余白で分ける。
3. ふたりの方向パッドは独立した主操作として、両盤面の直下に一つだけ配置。Utilityを無理に横へ詰めてキーを小さくしない。
4. 頻繁に使うボタンの位置とhit areaは、enable/disable・文言・状態で飛び回らない。
5. 完了時の進行CTAは、事前に確保した小さな結果領域などへ表示。盤面や操作位置を大きく跳ねさせない。
6. 上部は面番号と短い目的を優先。章の長い説明と補助機能を下へ押し広げる理由にしない。

## 3. Visual grammarと基準寸法

以下は今回の実装初期値/目標であり、万能な正解や適合認証ではない。実画面・英語・狭い幅を見て、同じ文法の範囲で微調整してよい。Humanへの色番号ごとの質問は不要。

| 要素 | 方針・初期値 |
|---|---|
| 形 | 制御UIは角丸8〜12px程度の短い長方形を基本。すべてをカプセルにしない |
| サイズ | 主要操作の実hit areaを最低44×44 CSS px。標準高48px、主操作/方向キーは48〜52pxを出発点にする |
| 間隔 | ボタン間8〜12px、操作群間16px程度。重なる透明hit areaで面積を水増ししない |
| 文字 | 既存のローカルfont/system fontを利用。操作文字は中太の読みやすいサンセリフ。通常14〜16 CSS px程度、主要ラベル16pxを出発点 |
| 見出し | 既存の絵本風見出しは保持可。操作ボタンまで細い明朝体に揃えない |
| アイコン | SVG等の実UI。20〜24px、同じstroke/角処理。Undoの折り返し矢印とRestartの周回矢印を区別 |
| 面 | Primaryは作品に合う十分濃い色＋読みやすい文字。Utilityは淡い面＋明確な文字。薄すぎて全ボタンdisabledに見える状態を避ける |
| 厚み | 1本の細い縁、薄い上面highlight、小さな下辺/影程度。大きい立体枠を何段も重ねない |
| 押下 | 視覚面だけ1px程度沈む/影が短くなる。クリック領域を動かさない。無駄な拡大縮小はなし |
| 反応 | 100〜160ms程度の短い反応を目安。入力処理を演出待ちにしない。reduced-motionでは変位/補間を止めても状態が分かる |
| フォーカス | キーボードで明瞭なfocus ring。overflowで切らない。装飾を優先して消さない |
| コントラスト | 通常文字4.5:1、識別に必要な非テキストの状態手掛かり3:1を目標に測定。inactive例外を全体の薄さの言い訳にしない |

### 作品差分は控えめに
- ひかり: 深い葉色を操作の軸にし、真鍮色は小さな縁や状態に限定。
- ふたり: 読みやすい中立の濃色を操作の軸にする。橙/紫はキャラクターの区別に残し、キーごとに派手な色を付けない。
- 配送: 濃い青緑を実行操作の軸にする。時計/注意の琥珀色とは役割を分ける。
- 新しい主張の強い配色で盤面Artを上書きしない。同じ寸法・アイコン文法・状態表現を共有し、3作品を色替えだけの同じ画面にしない。

### 状態の描き分け
| 状態 | Visual / behavior |
|---|---|
| 通常 | 読める名前、役割に応じた強さ、押せることが分かる |
| Hover | 対応pointer時のみ縁/面の微変化。必要情報をHoverだけへ隠さない |
| Pressed | 短い沈み/影の変化。一操作が二回発火しない |
| Focus-visible | 形の外に読み取れるring。モード切替後も操作先を見失わない |
| Disabled | 主張を下げ、機能を本当に無効化。理由は短い補助情報や必要時の説明で知れる |
| Running/Paused | アイコンとラベル両方で区別。回転中spinnerを飾りで常設しない |
| Clear | 盤面の達成を見せた後、「次へ」等を主操作に。自動遷移しない |
| Error | 失敗原因と修正手段を隣接。成功/危険を色だけで表さない |

## 4. 操作名と正確な意味

意味の変更を隠してラベルだけ短くしない。UIは既存の検証済みaction handlerを呼び、ルールを複製しない。

| 操作ID（概念） | 日本語 | English | 契約 |
|---|---|---|---|
| undo | 1手戻す | Undo | 今の作品の直前の有効操作を戻す。既存の履歴対象を維持 |
| restart-level | やり直す | Restart | この面の盤面を初期状態へ。全体のクリア履歴を消さない |
| start-run | 出発 | Go | 配送の現在の編集設定で一回の走行を開始 |
| pause-run | 一時停止 | Pause | 現在の論理状態を保持して停止。初期位置へ戻さない |
| resume-run | 再開 | Resume | 停止した論理状態から再開。二重timerを作らない |
| step-run | 1コマ | Step | 停止中に既存ルールで1tickだけ進行。秒と混同しない |
| edit-route | 調整に戻る | Edit route | 配置/待機設定を保持し、走行状態を初期位置に戻して編集へ |
| reset-layout | 初期配置に戻す | Reset layout | 配送の矢印/待機設定そのものを初期化。Edit routeと区別 |
| next-level | 次へ | Next | クリア後、次の既存問題へ。最終問では存在しないNextを出さない |
| levels | 面一覧 | Levels | 既存の面選択。新しい解放条件/課金/星評価を作らない |
| help/hint/settings | 遊び方 / ヒント / 設定 | How to play / Hint / Settings | 既存の内容と設定を保全して見せ方を整理 |

### 誤操作・初期化
- Undoに確認ダイアログは付けない。
- Restartは頻出操作として軽く保つ。ただし現在の試行を捨てる動作を、GoやNextと密着させない。
- 既存の安全なRestart挙動を確認。復旧不能な変更済み試行を捨てる場合は短い確認を用い、既に初期状態なら確認不要。確認は既存native dialog等を再利用し、新しいundo-after-reset機構は作らない。
- 配送で失敗後のPrimaryは原則Edit route。Reset layoutを誤って呼ばない。これにより調整のたびに確認を要求しない。
- 「全データ削除」はプレイ用の操作バーへ出さず、既存設定/内部管理領域に隔離する。
- 確認dialogはキャンセルを選びやすくし、閉じたら呼出元へfocusを返す。背後のゲームを勝手に動かさない。

## 5. 作品・状態別の操作配置

### Lightwork Garden
| 状態 | 主操作 | Utility / 補助 |
|---|---|---|
| 解答中 | 盤面の鏡操作。大きいStartは不要 | Undo / Restart、遊び方・ヒント・設定 |
| Undo履歴なし | 同上 | Undoは位置を維持して無効。Nextを大きく常設しない |
| ガイド/設定中 | 該当する案内操作 | modal/modelessを区別。閉じても状態を失わない |
| クリア後 | Next（最終面はLevels等の終了解説に合う操作） | Replay/Restart等はSecondary。花の達成演出を隠さない |

Undoは鏡だけでなく、既存の操作前の門状態も含めて戻る。見た目変更を口実に門の保持ルールを変えない。

### Two Ways Home
- D-padが主役。上下左右が規則的に並び、四つの個別buttonに同じ寸法と押下表現を用いる。
- 両盤面に対して共通のD-pad一つ。入力方向を両者へ短く示してよいが、実際に入力された方向だけを表示する。
- Undo / Restartはその下か、親指で邪魔にならない近接位置へ。解答中の無効Nextを目立たせない。
- 片方だけ帰宅した状態は全体クリアと区別。Primary Nextは二人同時に成功した後だけ。
- キーボードrepeat・pointer/click重複で一押しが二手にならない。移動数・無操作の履歴仕様を維持する。

### Tiny Delivery
| 状態 | Primary | Secondary / 状態表示 |
|---|---|---|
| 編集 | Go | 待機設定、必要時Reset layout、遊び方/ヒント/設定 |
| 走行 | Pause | Edit route。Step/配置編集は不可。再度Goを出さない |
| 一時停止 | Resume | Step / Edit route。1コマは論理1tickのみ |
| 失敗 | Edit route | 衝突地点と理由を残す。やみくもなResetで修正案を消さない |
| クリア | Next | Replay/Edit route等。配達完了を見せる |
| 最終面クリア | Levelsなど既存の終了導線 | 不正なNext、ランキング/公開共有機能の追加はなし |

実行状態は既存engineのstateから導出し、UI側に別の走行state machineを作らない。PrimaryのラベルがGo→Pause→Resumeと変わってもバー幅やpointerの位置が跳ねないようにする。

## 6. 入力・説明・アクセシビリティ

- 操作は原則native `button type="button"`。通常リンクとactionを区別し、`div onclick`だけの操作にしない。
- Enter/Spaceで一回だけ実行。ゲーム操作とbuttonのキー処理を重複させない。
- 矢印/WASDはゲームにfocusがあり、入力欄/select/dialog操作中ではない時に限る。ページ全体のscrollやブラウザshortcutを横取りしない。
- 危険なRキーなど、未説明のresetショートカットは増やさない。既存shortcutは維持し表示を短く整理可。
- 説明/設定dialogのopen/close/focus restorationを検証。非modalのチュートリアルへ偽の`aria-modal`を付けない。
- トグルは固定名＋押下状態、action名が変わるPause/Resumeは通常button等、選んだ意味に整合させる。
- 撮影で非表示にするUIは、透明なままfocus可能に残さない。操作導線そのものを失わせない。
- ヒント・説明を整理しても、初見の遊び方を削除しない。最初の一手、門保持、同時帰宅、配送編集/走行の区別は従来の図解/実操作で学べるよう保全する。
- 装飾音・press motionは任意/軽量。mute/reduced-motionを尊重。録画映えのための点滅・flash・激しい画面揺れは追加しない。

# Part II — 通常・縦撮影・横撮影の表示契約

## 7. 基本方針

> **ゲームは一つ。縦横で変えるのは器とUI配置。問題・駒の座標系・ルール・正解・保存・Undo履歴を変えない。**

| モード | 表示 | 用途 |
|---|---|---|
| auto | 通常レスポンシブ | 初見ユーザー/通常プレイ。実viewportに合わせる |
| portrait | 9:16の撮影領域 | 縦動画をPCでも撮りやすくする |
| landscape | 16:9の撮影領域 | 横動画の実況/攻略素材 |

「長編」と「横」は別。動画の長さを制限/判定する機能はない。1080×1920と1920×1080は録画出力の基準候補であり、CSSサイズをその値へ固定する指示ではない。

- 設定内の「撮影用レイアウト」から3択。トップへ常時大きなモード切替を置かない。
- 初期はprototype/内部制作環境だけで利用。アカウント、権限システム、新しい公開サービスを作らない。
- Autoを標準。選択の記憶が必要なら表示設定専用のsessionStorage等へ。保存不可でも切替可能とし、ゲーム進行用schemaを変更しない。
- QA/制作向けにenum限定のlayout queryを付けた直リンクを用意してよい。ゲーム名/文言へ生queryをHTML挿入しない。公開権限を与えるパラメータにはしない。
- 現在のprototype buildに組込み、通常/Design出力への漏洩防止を維持する。

## 8. 撮影枠・サイズ・余白

- 安定した識別子（例 `data-capture-frame`）を持つ撮影領域を一つ定める。ゲーム＋必要なHUD/操作を含み、Portal周辺、設定UI、レビュー情報は含めない。
- 9:16/16:9を保つ枠の中で盤面とUIを**再配置**する。横長のページ全体を9:16へ縮小する、正方形を縦に伸ばす、端の駒をcropする方法は禁止。
- 盤面のcell aspectは保持。Two Ways Homeも盤面自体は回転させない。見た目を変えて解法を変えない。
- ゲームがiframe内にあるため、外側window幅だけでなく実際のgame containerの有効サイズを基準にする。CSSのGrid/Flex/aspect-ratioを優先し、必要時だけ既存描画にResizeObserverを加える。
- 描画面とpointer座標を一致させる。DPR、CSS scale、スクロール、offset、orientation変更を含めて実位置をテスト。全UI一括transform縮小で44px操作を見かけだけ満たさない。
- 写す領域にscrollbarを常設せず、ガイドを閉じた通常撮影状態では全盤面と主要状態を1フレームへ収める。
- 字幕/UI被りを避ける任意の構図ガイドを、撮影領域外の制作側コントロールからON/OFFできる。初期はOFF。投稿サービスの公式safe zoneとして寸法を断定しない。
- 上下の字幕用余白は小さく可変にし、巨大な空帯のために盤面を縮めない。右端/最下部へ重要な目的地を無理に寄せず、最終的な投稿プレビューで確認する前提を記録する。
- 補助UIの省略は長文説明/章一覧/内部QAなどから行う。勝敗を理解する目標や実操作手段を先に消さない。
- 撮影modeのexit/settingsは撮影枠の外で常に見つけられ、Tabでも到達できる。録画開始後の自動隠蔽など複雑なcontrollerは作らない。

### 小さい端末での扱い
通常mobileはAutoが第一。撮影の横枠を縦向きスマホへ無理にfitし、読めない/押せない画面を完成扱いにしない。

- 有効サイズで両立できる範囲では、装飾と余白を減らしてから盤面を調整。
- 16:9撮影等で必要なサイズを確保できない時は、選択を密かに変えず、「この幅では通常表示が遊びやすい」等の短い案内とAutoへ戻る操作を撮影枠外に出す。
- 選択維持と復帰を保証し、OSの強制回転・fullscreen許可に依存しない。
- 本番の対応端末制限をこの作業だけで確定しない。限界をQAに明記する。

## 9. 作品ごとの配置

### Lightwork Garden
- portrait: 短い目標/面番号 → 大きな正方形盤面 → 花/門の状態とコンパクトな操作。長い説明カードは常設しない。
- landscape: 正方形盤面を主役に、横の空間へ短い目標/門・花の状態/必要なガイド。余白を埋めるための文章を増やさない。
- 光源から花までの経路を切らない。分光器や門がフレーム外になる構成はNG。

### Two Ways Home
- portrait: 二つの盤面を上下に置く。常に両者が同時に見える。
- landscape: 二つの盤面を左右へ。共通D-padは一つ。
- どちらも両盤面のcell size/向き/解像感を揃える。片側だけ拡大、交互表示、別タブ化は禁止。
- 「左/右の庭」など配置に依存する文を使わず、既存のキャラクター名・形・記号で示す。
- portraitでは外枠/章/装飾余白から削り、両盤面＋共通入力＋目的が読める寸法を確保する。二面という制約を隠さない。

### Tiny Delivery
- portrait: 盤面＋配達数/走行状態を中央へ。時計の待機設定と該当地点の対応を近くにまとめる。
- landscape: 盤面の横に待機/状態/短い解説を置けるが、大きな管理画面にしない。
- 編集/走行/Pause/失敗/配達済みが動画で識別可能。ルート、二台、目的地、衝突地点を全部見せる。
- 現在の失敗原因の保持とEdit routeの復帰を維持する。

## 10. 状態維持と一時停止

モード切替はゲームのrestartではない。原則同じengine/iframe/DOM内でlayoutのみ変更する。

1. 入力中/animation中は既存の一手を整合した境界まで処理する。新しい入力を二重適用しない。
2. 配送が走行中なら安全な論理tick境界でPauseへ移し、その地点を維持してレイアウトを変える。
3. 表示後にframe数や経過実時間を使って先へ進めない。利用者がResumeするまでは停止を維持する。
4. 既にPause/失敗/クリア/ガイド表示中なら、その状態を維持する。
5. `currentLevel`、盤面/駒、鏡/門、経路/待機、配送tick、Undo履歴、ヒント段階、完了履歴は切替前後で一致。配送のrunning→paused等、許可したphase差だけを検証から区別する。
6. mode変更をゲーム進行の保存イベント/新しいfirst input/clearとして数えない。セッションの表示設定は別に扱う。
7. save reset/schema移行は追加しない。既存の保存失敗・不正保存の保持、別ゲーム非干渉を壊さない。
8. 模擬広告、設定dialog、pagehideなど複数の停止理由が重なった場合、片方を閉じただけで残る停止理由を無視して再開しない。
9. URL再読込が必要な直リンクでは、通常の既存restore仕様を適用する。表示設定の切替そのものと、ページ再読込によるセーブ復元を混同しない。

## 11. 一括で進める内部順序

1. R2を開き、操作バーと各modeで必要な情報/実actionを確認。Beforeを記録。
2. 共通操作UIとstate別button modelを局所的に設計。Astraが実画面で判断し、この段階だけでHumanへ差し戻さない。
3. 一つの代表画面で通常時/pressed/disabled/clearを仕上げ、同じ文法を3作品へ展開。
4. 既存の描画/接続を保ちながら3モードのlayoutを追加。
5. 少なくとも導入・中盤・終盤、英語の長い表示、配送Pause/失敗を実際に操作して自己修正。
6. 回帰・state preservation・出力隔離・Security・path安全性を検証。
7. 1つのレビューHTMLまたは既存の同等形式へ、URL・比較・制約をまとめる。Humanレビュー待ちで停止。

一括作業とは、各段階でHuman承認を取り直さず完遂することであり、共有ファイルへの無制御な並列書込ではない。担当/統合境界は既存AGENTSに従う。

## 12. QA — Test PASSと商品受入を分ける

### 既存の保全
- 開始時のlevel/rule/Art hashと比較し、54問の意味・18問×3作品を維持したことを確認。
- ルール変更なしなら全54問の既知解答を現engineで自動再生し、既存の中間assertを利用。表示全パターンで同じ54問を毎回総当たりする必要はない。

- secret scan、diff、空白/日本語pathの包含と拒否テスト。新しい検出例外を自動追加しない。

### 操作/state
- Undoなし/あり、門を開けてUndo、二人移動とUndo、Restartの対象範囲。
- 配送のGo→Pause→Step→Resume→失敗→Edit route→再出発→clear。設定が保たれること。
- Nextは未クリアでは進めず、最終面で存在しない面へ進めない。勝手なunlock条件の追加なし。
- pointerupとclick、Enter/Space、keydown repeatの多重発火なし。mode変更中の連打も確認。
- confirmのcancel/accept、Escape、focus restoration、game inputとdialog入力の分離。
- disabledが視覚だけでなく機能的にも無効であること。

### 3モードとレイアウト
- 3作品×3モード×日英について、導入/中盤/最終面の代表場面で、盤面・主要操作・補助UI・英語の切れ/重なりを確認。

- Portraitの代表的な撮影枠は360×640または432×768 CSS px程度で検証。Landscapeは960×540程度を基準に、実際の利用領域で可読性/操作性を検証。
- 1080×1920、1920×1080の画像を出す場合、適切なDPR等で実ブラウザを描画して領域をclipする。低解像画像の拡大を高解像描画と偽らない。実CSS寸法/DPR/出力pxを記録。
- 保存せず進行中にAuto→Portrait→Landscape→Autoと切替え、状態一致を検証。配送はrunning→paused以外の状態が動かないこと。旧save、言語/再読込も回帰。
- 実際のgame container内でpointerの当たりが一致。fullscreen/iframe/入れ子表示が必要なら実際の経路で検証。
- guide OFFの撮影枠は全主要要素が収まる。guide ONやhelp開閉でも入力可能性と閉じる導線を失わない。
